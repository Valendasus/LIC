## Learn

### Суть за минуту

Когда асинхронных операций несколько, нужно решить, **чего ждать**: всех, первой успешной, первой любой или всех, но без отказа из-за одной ошибки. На каждый случай есть свой метод `Promise`:

```js
const [user, posts] = await Promise.all([getUser(id), getPosts(id)]) // нужны оба
const results = await Promise.allSettled(widgets.map(load)) // нужны все исходы
const file = await Promise.any(mirrors.map(download)) // нужен первый успех
const first = await Promise.race([load(), timeout(5000)]) // кто первый завершится
```

Все четыре запускают ожидание **параллельно** и **ничего не отменяют**.

### Четыре комбинатора

| Метод | Выполняется | Отклоняется | Пустой вход |
|---|---|---|---|
| `Promise.all` | все выполнены — массив значений по порядку входа | при **первой** ошибке | сразу `[]` |
| `Promise.allSettled` (ES2020) | все завершены — массив `{ status, value \| reason }` | никогда | сразу `[]` |
| `Promise.race` | первым завершившимся | первым завершившимся | **никогда не завершится** |
| `Promise.any` (ES2021) | первым **успехом** | все отклонены — `AggregateError` | сразу отклонён |

Общие правила:
- на вход подходит **любое итерируемое**: массив, `Set`, генератор;
- не-промисы оборачиваются через `Promise.resolve`, то есть считаются уже выполненными;
- комбинатор подписывается на **все** входные промисы, поэтому их отклонения не становятся «необработанными».

### Promise.all — нужно всё

Результаты идут в порядке **входа**, а не завершения — поэтому деструктуризация надёжна:

```js
const [user, settings, permissions] = await Promise.all([
  getUser(id),
  getSettings(id),
  getPermissions(id),
])
```

**Fail-fast:** первая ошибка сразу отклоняет результат. Остальные промисы при этом продолжают выполняться: их ответы просто никто не ждёт.

Когда подходит: все данные обязательны, без любого из них экран не имеет смысла.

### Promise.allSettled — частичный успех

Ждёт все промисы и никогда не отклоняется. Каждый исход описан объектом:

```js
const results = await Promise.allSettled(files.map(upload))
const failed = results
  .map((result, i) => ({ result, file: files[i] }))
  .filter(({ result }) => result.status === 'rejected')
if (failed.length) showError(`Не загрузились: ${failed.map(({ file }) => file.name).join(', ')}`)
```

Когда подходит: массовые операции, где нужно знать, что получилось, а что нет, — загрузка файлов, рассылка, дашборд.

### Promise.race — первый завершившийся

Берёт первый **завершившийся** промис — успехом **или** ошибкой. Классическое применение — гонка с таймаутом:

```js
function timeout(ms) {
  return new Promise((_, reject) => setTimeout(() => reject(new Error('Timeout')), ms))
}
const data = await Promise.race([loadReport(), timeout(5000)])
```

<Callout type="mistake" title="Таймаут через race, который ничего не отменяет">
Когда `loadReport()` ответил, таймер продолжает висеть до срабатывания. Когда сработал таймаут, запрос продолжает работать и грузить сеть. Для `fetch` правильнее `fetch(url, { signal: AbortSignal.timeout(5000) })` — запрос действительно отменится. В своём коде очищайте таймер в `finally` (задача «Промис с таймаутом» в теме «Event loop»).
</Callout>

**`Promise.race([])` никогда не завершится.** Если список может оказаться пустым, проверяйте это заранее.

### Promise.any — первый успех

Пропускает ошибки и ждёт первый **успешный** результат. Если отклонены все — бросает `AggregateError`, все причины лежат в поле `errors`:

```js
try {
  const config = await Promise.any([fromCache(), fromCdn(), fromOrigin()])
  apply(config)
} catch (error) {
  // error instanceof AggregateError
  report(error.errors)
}
```

Когда подходит: несколько равноценных источников — зеркала, резервные серверы, кэш и сеть.

### Комбинаторы ничего не отменяют

Это главная ловушка темы. После победы в `race` или `any` и после отклонения `all` остальные операции **продолжают работать**. Если они не нужны, отменяйте их сами — через общий `AbortController`:

```js
async function fastest(urls) {
  const controller = new AbortController()
  try {
    return await Promise.any(urls.map((url) => fetch(url, { signal: controller.signal }).then((r) => r.json())))
  } finally {
    controller.abort() // остальные запросы больше не нужны
  }
}
```

`abort()` после того, как победитель уже ответил, на него не влияет: отменяются только незавершённые запросы.

### Как выбрать

| Ситуация | Комбинатор |
|---|---|
| все данные обязательны | `all` |
| нужен результат каждой операции, ошибки не должны мешать остальным | `allSettled` |
| несколько равноценных источников, нужен любой рабочий | `any` |
| важно, кто первый завершится, — таймаут, «кто быстрее» | `race` |
| много операций, но не больше N одновременно | ни один — пул задач (задача `mapLimit` в теме «Event loop») |

<Example file="src/widgets/dashboard/load.ts" verdict="good">

Главный экран загружает шесть блоков. Обязательные — профиль и права — идут через `Promise.all`: без них экран не показать, и ошибка ведёт на страницу ошибки. Остальные блоки — через `Promise.allSettled`: упавший виджет показывает «Не удалось загрузить» с кнопкой «Повторить», остальные работают. На сервере это одна функция подготовки данных, на клиенте каждый виджет грузится сам.

</Example>

<Example file="src/shared/api/search.ts" verdict="review">

```js
const results = await Promise.race(
  providers.map((provider) => provider.search(query)),
)
```

Задумано «взять самый быстрый поисковый сервис». Но если первым быстро упадёт один провайдер, `race` вернёт ошибку, хотя остальные ещё отвечают. Нужен `Promise.any`, а проигравшие запросы стоит отменить через `signal`. И если `providers` пустой, `race` повиснет навсегда — нужна проверка.

</Example>

### Новое: Promise.allKeyed

Предложение TC39 **Await Dictionary** на стадии 3 добавляет `Promise.allKeyed` и `Promise.allSettledKeyed`. Они принимают объект и возвращают результаты по тем же ключам:

```js
const { user, posts } = await Promise.allKeyed({ user: getUser(id), posts: getPosts(id) })
```

Так нельзя перепутать позиции при деструктуризации массива. В браузерах этих методов пока нет; написать свою версию — задача в практике.

<Callout type="deep">
- **Как они устроены.** Каждый комбинатор вызывает `this.resolve(item)` для каждого элемента и подписывается на него через `then`. Поэтому они работают с подклассами `Promise` и принимают thenable. Итерируемое перебирается целиком сразу.
- **Почему пустой `race` висит.** Чтобы завершиться, `race` ждёт, что какой-нибудь промис вызовет его `resolve` или `reject`. В пустом списке звать некому. У `all` и `any` для пустого входа есть явная ветка в спецификации.
- **Порядок `errors` у `AggregateError`** — по входу, а не по времени, как и порядок значений у `all`.
</Callout>

### Частые ошибки

| Ошибка | Признак | Исправление |
|---|---|---|
| `all` там, где нужен частичный успех | один сбой прячет все данные | `allSettled` или отдельные запросы |
| `race` там, где нужен первый успех | быстрая ошибка побеждает рабочий ответ | `any` |
| таймаут через `race` без очистки | висящие таймеры, запрос не отменяется | `AbortSignal.timeout`, очистка в `finally` |
| ожидание, что проигравшие отменятся | лишние запросы в сети | общий `AbortController` |
| пустой вход в `race` | промис висит вечно | проверка длины |
| `all` на тысячи запросов | браузер и сервер захлёбываются | пул с ограничением параллельности |

<Callout type="interview">
Попросят объяснить разницу четырёх методов и написать свой `Promise.all` — он есть в практике темы «Event loop», здесь — `allSettled` и `any`. Сильный ответ добавляет три вещи: результаты идут в порядке входа; комбинаторы ничего не отменяют, и как это исправить через `AbortController`; как ведёт себя пустой вход.
</Callout>

4. **`race`** с таймаутом, а лучше `AbortSignal.timeout(300)` в `fetch`: опоздавший запрос отменится. Плюс отмена предыдущего запроса при новом вводе.
5. **Ни один** — нужен пул с ограничением в 5 одновременных (задача `mapLimit`), а для результатов — подход как у `allSettled`.

## Confirm

<Question q="Чем отличаются Promise.all, allSettled, race и any?">
`all` — все выполнены, первая ошибка отклоняет. `allSettled` — ждёт все и никогда не отклоняется, отдаёт статус каждого. `race` — первый завершившийся, успех или ошибка. `any` — первый успех; если отклонены все — `AggregateError`.
</Question>

<Question q="Что происходит с остальными операциями после отклонения all или победы в race?">
Они продолжают выполняться: комбинаторы ничего не отменяют. Если операции не нужны, им передают общий `AbortSignal` и вызывают `abort()` после победы или ошибки.
</Question>

<Question q="Как комбинаторы ведут себя с пустым массивом?">
`all` и `allSettled` сразу выполняются с `[]`, `any` сразу отклоняется с `AggregateError`, `race` не завершается никогда.
</Question>

<Question q="Почему таймаут через Promise.race — не полноценная отмена?">
`race` только перестаёт ждать: сам запрос продолжает работать, а таймер висит до срабатывания, если его не очистить. Для `fetch` правильнее `AbortSignal.timeout(ms)`.
</Question>

<Question q="Когда allSettled лучше all?">
Когда операции независимы и сбой одной не должен скрывать результаты остальных: массовая загрузка, рассылка, дашборд. `all` уместен, когда без любого результата продолжать нельзя.
</Question>
