## Learn

### Суть за минуту

JavaScript на странице выполняется в **одном потоке**. Пока ваш код работает, браузер не может ни обработать клик, ни перерисовать экран. Асинхронность устроена не внутри JS: таймеры, сеть и события обслуживает браузер, а готовые колбэки ставит в **очереди**. Цикл событий (event loop) по одному берёт их оттуда, когда стек вызовов пуст.

### Из чего состоит

| Часть | Что это | Примеры |
|---|---|---|
| **Стек вызовов** | Функции, которые выполняются прямо сейчас | Ваш код |
| **Очереди задач** (macrotasks) | Колбэки, готовые к запуску. По спецификации их несколько, браузер сам выбирает, из какой брать | Скрипт целиком, `setTimeout`, `setInterval`, события ввода, `message` от воркера, ответ на `postMessage` |
| **Очередь микрозадач** | Колбэки, которые выполняются сразу после текущей задачи, до всего остального | Реакции промисов (`then`, `catch`, `finally`), продолжение после `await`, `queueMicrotask`, `MutationObserver` |
| **Отрисовка** | Обновление экрана, когда браузер решит, что пора (обычно под частоту экрана) | Колбэки `requestAnimationFrame`, стили, layout, paint |

### Один оборот цикла

1. Взять **одну** задачу из очереди задач и выполнить её до опустошения стека.
2. **Контрольная точка микрозадач:** выполнить все микрозадачи. Если микрозадача добавила новые, выполнить и их — до полного опустошения очереди.
3. Если пришло время кадра — **отрисовка**: колбэки `requestAnimationFrame`, пересчёт стилей и layout, paint.
4. Перейти к шагу 1.

Из этого следуют три правила, на которых держатся почти все задачи собеседований:

- **Синхронный код всегда идёт первым.** Таймер с задержкой 0 не означает «сразу», он означает «не раньше следующей задачи».
- **Микрозадачи выполняются раньше любой следующей задачи.** Промис всегда обгоняет `setTimeout`.
- **Отрисовка не может вклиниться в задачу и в очередь микрозадач.** Пока они идут, экран заморожен.

```js
console.log('1: синхронно')
setTimeout(() => console.log('4: задача'))
Promise.resolve().then(() => console.log('3: микрозадача'))
console.log('2: синхронно')
// 1, 2, 3, 4
```

### async/await — это промисы

`async`-функция выполняется **синхронно до первого `await`**. Всё, что после `await`, становится микрозадачей, которая запустится, когда ожидаемый промис выполнится.

```js
async function load() {
  console.log('b')
  await null
  console.log('d')
}
console.log('a')
load()
console.log('c')
// a, b, c, d
```

Функция внутри `new Promise((resolve) => …)` тоже выполняется синхронно, асинхронны только обработчики `then`.

### Почему замерзает страница

```js
button.addEventListener('click', () => {
  const sorted = hugeArray.toSorted(compare) // 800 мс
  render(sorted)
})
```

Пока сортировка идёт, стек не пуст: клики копятся, анимации стоят, курсор в поле ввода не мигает. Задача длиннее 50 мс считается **длинной** и ухудшает метрику INP (Interaction to Next Paint): хорошим считается отклик до 200 мс.

**Что делать:**

| Подход | Когда |
|---|---|
| Разбить работу на порции и уступать поток между ними | Работа делится на части: обработка списка, экспорт |
| Перенести в Web Worker | Тяжёлые вычисления, которым не нужен DOM |
| Отложить несрочное: `useTransition` в React, `requestIdleCallback` | Обновление можно показать чуть позже |
| Не делать вовсе: виртуализация, пагинация на сервере | Работа не нужна пользователю целиком |

Уступить поток можно через `setTimeout(resolve)` или `scheduler.yield()`. Последний продолжает работу с более высоким приоритетом, чем обычный таймер, но поддерживается не во всех браузерах — проверяйте на MDN и держите запасной вариант.

<Callout type="mistake" title="Разбивать работу микрозадачами">
`await Promise.resolve()` между порциями **не уступает поток**: микрозадачи выполняются до отрисовки, все подряд. Страница будет заморожена так же, как без разбиения. Уступает только новая задача: `setTimeout`, `scheduler.yield()`, `MessageChannel`.
</Callout>

<Example file="src/pages/registry/export.ts" verdict="good">

Выгрузка CSV на 20 000 строк собирается порциями по 2 000 строк. Между порциями вызывается `await nextFrame()`, где `nextFrame = () => new Promise((resolve) => setTimeout(resolve))`. Таймер — это новая задача, поэтому браузер успевает обработать клики и перерисовать кнопку «Готовим файл…».

</Example>

<Example file="src/api/registry.worker.ts" verdict="good">

Фильтрация и сортировка 100 000 записей вынесены в Web Worker: у воркера свой поток и свой цикл событий. В основной поток возвращается только массив id. Ответ воркера приходит как событие `message` — обычная задача в очереди основного потока.

</Example>

### Где в цикле requestAnimationFrame

Колбэки `requestAnimationFrame` выполняются **перед отрисовкой кадра**, примерно с частотой экрана, и приостанавливаются в фоновой вкладке. Поэтому анимации делают через `rAF`, а не через `setInterval`: таймер не привязан к кадрам и даёт рывки.

<Callout type="deep">
- **Минимальная задержка таймера.** По спецификации HTML вложенные таймеры (с уровня вложенности больше 5) получают задержку не меньше 4 мс. В фоновых вкладках браузеры замедляют таймеры ещё сильнее.
- **Очередей задач несколько.** Спецификация разрешает браузеру отдавать приоритет, например, вводу пользователя перед таймерами. Порядок двух `setTimeout` между собой гарантирован, а порядок таймера относительно клика — нет.
- **Node.js** устроен иначе: у libuv фазы (таймеры, ввод-вывод, `setImmediate`), а очередь `process.nextTick` выполняется даже раньше промисов. Это отдельная тема в блоке Backend.
</Callout>

## Confirm

<Question q="Опишите один оборот цикла событий в браузере.">
Взять одну задачу и выполнить до опустошения стека; затем выполнить все микрозадачи, включая добавленные по ходу; затем, если пора, отрисовать кадр (колбэки `requestAnimationFrame`, стили, layout, paint); повторить.
</Question>

<Question q="Что относится к микрозадачам, а что к задачам?">
Микрозадачи: реакции промисов (`then`, `catch`, `finally`), продолжения после `await`, `queueMicrotask`, `MutationObserver`. Задачи: выполнение скрипта, `setTimeout` и `setInterval`, события ввода, `message` (в том числе от воркеров и `MessageChannel`).
</Question>

<Question q="Почему await Promise.resolve() не помогает разбить тяжёлую работу?">
Это микрозадача. Все микрозадачи выполняются подряд до отрисовки, поэтому браузер так и не получит возможности обработать ввод и обновить экран. Уступить поток можно только новой задачей: `setTimeout`, `scheduler.yield()`, `MessageChannel`.
</Question>

<Question q="Чем requestAnimationFrame лучше setInterval для анимации?">
Колбэк вызывается прямо перед отрисовкой, синхронно с частотой экрана, и приостанавливается в фоновой вкладке. Таймер не привязан к кадрам: кадры пропускаются или рисуются дважды, анимация дёргается.
</Question>

<Question q="Что такое длинная задача и как она связана с INP?">
Задача дольше 50 мс. Пока она выполняется, браузер не может отреагировать на ввод, поэтому время от действия пользователя до следующей отрисовки растёт. INP хорош до 200 мс; длинные задачи — главная причина плохого INP.
</Question>

<Callout type="interview">
Почти на каждом фронтенд-собеседовании дают 2–3 задачи «что выведет» с `setTimeout`, промисами и `async`. Проговаривайте вслух: «синхронно → микрозадачи → задача». Сильный кандидат добавляет, где в цикле отрисовка и почему из-за этого тяжёлый код замораживает интерфейс.
</Callout>
